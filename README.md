# 基于 LangChain 的 RAG 企业级电商知识库问答系统

毕业设计项目。用户在浏览器里就能对商品知识库提问，系统检索商品资料后生成回答，
并在回答里标出「这句话是根据哪份资料的哪一段来的」，点开可以看原文。

---

## 快速开始

### 第一次运行

**1. 准备后端环境**（需要 Python 3.10 以上，本项目在 3.14 上开发）

```bash
cd backend
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
```

**2. 配置 API Key**

```bash
copy .env.example .env
```

然后打开 `backend\.env`，把 `DASHSCOPE_API_KEY` 填成你自己的阿里云百炼 API Key。
还没有的话去 <https://bailian.console.aliyun.com/> 免费注册一个，新用户有免费额度。

**3. 安装前端依赖**

```bash
cd ../frontend
npm install
```

### 日常启动

双击项目根目录的 **`start.bat`** 即可，它会自动拉起前后端并打开浏览器。

也可以手动分别启动：

```bash
# 后端（在 backend 目录下）
.venv\Scripts\python.exe -m uvicorn app.main:app --reload --port 8000

# 前端（在 frontend 目录下）
npm run dev
```

启动后访问：

| 地址 | 说明 |
|------|------|
| <http://localhost:5173> | 前端页面 |
| <http://127.0.0.1:8000/docs> | 后端接口文档（可直接在里面试接口） |

### 默认账号

| 用户名 | 密码 | 角色 |
|--------|------|------|
| `admin` | `123456` | 管理员，可管理知识库、看统计看板 |

普通用户请在前端页面自行注册。

## 功能一览

- **知识库管理**（仅管理员）：新建多个知识库，上传 PDF / Word / Excel / TXT / Markdown，
  系统自动解析、切分、向量化入库；支持删除与重建索引
- **知识库问答**：流式输出（打字机效果），回答带 `[1][2]` 引用标注，右侧面板可展开原文对照
- **多用户多会话**：每个用户有自己的会话列表，数据严格隔离；支持按标题搜索会话
- **历史对话**：退出后重新登录，之前的对话和引用都能完整找回
- **账号体系**：注册、登录、修改密码；改密后其它设备自动下线
- **答案反馈**：对回答点赞/点踩（可附原因），个人中心能看到自己给过的评价
- **统计看板**（仅管理员）：问答量、Token 消耗、缓存命中率、平均响应延迟、
  **平均首字延迟**、满意度；问答趋势折线图、高频问题排行、
  以及「最近被点踩的回答」——管理员靠它发现知识库该补哪方面的资料

## 技术栈

| 层 | 选型 | 说明 |
|----|------|------|
| 大模型 | 阿里云百炼 · 通义千问 | 对话 `qwen-plus`，向量化 `text-embedding-v3`，重排 `gte-rerank-v2` |
| 编排框架 | LangChain 1.x | 直接用 LCEL 管道，不依赖已弃用的 `langchain-community` |
| 后端 | Python + FastAPI + SQLAlchemy | 全异步，自动生成接口文档 |
| 向量库 | Chroma | 嵌入式，不需要额外装数据库服务 |
| 关系库 | SQLite | 开了 WAL 模式提升并发；代码按可切 PostgreSQL 编写 |
| 前端 | Vue 3 + Vite + Element Plus + Pinia | |

### 关于技术选型的一个说明

网上大量 LangChain 教程用的是 `ChatTongyi`、`DashScopeEmbeddings`、`EnsembleRetriever`
这些组件，它们来自 `langchain-community` 包——**该包已被 LangChain 官方弃用并归档，不再接收安全补丁**。

本项目因此另走一条路：对话模型用官方维护的 `langchain-openai` 指向百炼的 OpenAI 兼容端点，
向量化、重排、中文 BM25 检索、RRF 融合这四个组件自己实现（封装在 `backend/app/rag/` 下，
每个只有几十行）。好处是依赖干净、可控，也避免了跟着弃用组件一起被淘汰。

## 优化效果（实测数据）

### 检索效果对比

30 个标注问题、5 种配置的对比实验，跑 `python scripts/eval_rag.py` 可复现：

| 配置 | Recall@1 | Recall@5 | MRR | 平均延迟 |
|------|----------|----------|-----|---------|
| ① 纯向量检索 | 83.3% | **100%** | 0.893 | 159ms |
| ② 纯关键词检索 | 60.0% | 86.7% | 0.708 | 14ms |
| ③ 混合检索 | 83.3% | 96.7% | 0.894 | 149ms |
| ④ 纯向量 + 重排 | 83.3% | 93.3% | 0.883 | 268ms |
| ⑤ 混合检索 + 重排 | 83.3% | 93.3% | 0.883 | 274ms |

> **一个诚实的结论**：在本项目的语料规模（54 个分块）上，
> **混合检索相比纯向量没有带来额外收益，重排也没有提升指标**。
> 原因不是"混合检索没用"，而是"这个规模下没用"：
> BM25 依赖的词频统计在这么小的语料上不可靠，
> 而且测试问题偏口语化，BM25 结构上就匹配不上。
> 语料规模上去之后它的价值会体现，所以能力保留着、可配置切换。

**收益最大的一项优化是「分块上下文增强」**：分块时给每块补回来源标题
（`【云驰 AirBook 14 · 电池与续航】`），解决"手机和笔记本的电池段落分不清"的问题。
修复后 BM25 的 MRR 提升 **29%**，向量检索的 Recall@5 达到 **100%**。

### 流式输出的感知提速

| 方式 | 用户开始看到内容 | 总耗时 |
|------|----------------|--------|
| 非流式 | 13.8 秒（界面无任何变化） | 13.8s |
| 流式 | **0.3 秒** | 15.1s |

总耗时几乎一样，但**用户感知的等待时间相差 98%**。
这是「平均首字延迟」这个指标存在的意义——只看平均响应延迟的话，
这个优化在数字上完全体现不出来。

### 过程中的几个工程问题

开发中修掉的、值得记录的坑（都写进了代码注释）：

- **缓存命中率恒为 0**：写日志时代码把 `cache_hit` 写死成 `False`，
  参数传进来了却被忽略。问答功能完全正常，只有看板的数字不对
- **限流器定义了但没接进请求链路**：登录接口可以被无限次暴力破解
- **Chroma 冷启动并发竞争**：首次提问时两路检索同时建客户端，
  导致句柄失效、报出与业务无关的错误
- **外部接口默认超时长达 5 分钟**：配上重试，网络一抖动单次检索能卡 197 秒，
  而且全程没有任何报错，界面看起来就是卡死
- **批量重建索引打爆数据库连接池**：17 份文档同时处理，
  每个任务独占一个连接不释放，后续全部超时失败，
  界面上只表现为"文档一直卡在处理中"

## 常见问题

**Q：提示「无法连接服务器」怎么办？**
后端没启动。双击 `start.bat`，或确认那个标题为「RAG后端」的窗口还在运行。

**Q：上传文档后一直是「处理中」？**
先去检查 `backend\.env` 里的 `DASHSCOPE_API_KEY` 是否填对了。向量化需要调用云端接口，
Key 不对就会一直失败。可以在「知识库管理」页看到具体的报错信息。

**Q：会不会产生费用？**
会产生。对话和向量化都按用量计费。百炼新用户有免费额度，毕设演示的量完全够用。
想省钱可以把 `.env` 里的 `LLM_MODEL` 换成 `qwen-turbo`（更便宜），
并在「统计看板」里关注 token 消耗。
